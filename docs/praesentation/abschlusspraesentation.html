Anhang B1 · Zugriffskontrolle

Rechte-Matrix — und eine geschlossene Lücke

Die Matrix liegt in server/auth.js (ROLLEN_RECHTE) und wird von der Middleware requireAuth(recht) pro Route erzwungen. Die UI blendet zusätzlich aus.
AktionempfangprueferchefRecht
Lesen (alle GET-Endpunkte)✓✓✓lesen
Halter / Fahrzeuge / Termine anlegen und ändern✓✓✓schreiben
Status setzen über PATCH /api/termine/:id/status✗✓✓status
Mängel anlegen und entfernen✗✓✓status
Löschen · /api/admin/* (zusätzlich X-Admin-Token)✗✗✓loeschen
Status über den generischen PATCH /api/termine/:id ✗✗✗ gar nicht — HTTP 400

Was hier offen war

Der generische PATCH /api/termine/:id nahm statusCode entgegen und verlangte nur schreiben; POST /api/termine übernahm einen mitgelieferten Status. Die Rolle empfang konnte damit ein Prüfergebnis setzen — die Matrix galt an dieser Stelle nur auf dem Papier.

Wie es geschlossen wurde

statusCode ist aus dem PATCH-Mapping entfernt und wird mit 400 abgelehnt statt still ignoriert; POST /api/termine legt jeden Termin als Geplant an. Damit bleibt genau eine Route für Statusänderungen — die einzige mit requireAuth("status") und WF-01-Guard. Abgesichert durch Regressionstests in termin-status-routen.test.js (ADR-003, Nachtrag).

Fail-closed: Unbekannte Rollen liefern in ROLLEN_RECHTE immer false. Ohne gültigen Token 401, bei unzureichender Rolle 403. Grenze: Das Rollenmodell wirkt an der API. Wer direkt in die Datenbank schreibt, umgeht es — dagegen wirken der WF-01-Trigger und die Bindung des DB-Ports an 127.0.0.1.

Anhang B3 · Schema-Evolution

Versionierte Migrationen und Desired-State-Objekte (ADR-011)

Zwei bewusst getrennte Mechanismen: Schemaänderungen laufen genau einmal, Seeds und Trigger bei jedem Start.

Versioniert — genau einmal pro Datenbank

Buchführung in schema_migration mit Version, Name und Zeitstempel. Append-only: ausgelieferte Migrationen werden nie editiert — Bestandsinstallationen haben sie schon protokolliert. Änderung = neue Version.

VNameInhalt
1initial-schemadie 8 Fachtabellen — mit IF NOT EXISTS, damit Bestandsinstallationen sie als No-op durchlaufen
2hu-richtlinie-kategorienAlt-Kategorien → OM/GM/EM/GfM; FK ON UPDATE CASCADE benennt die Mangel-Zeilen mit um. Korrigiert auch, dass EM früher nicht blockierte.
3benutzer-tabelleLogin-Konten der drei Rollen (CHECK auf die Rolle)

GET_LOCK gegen parallele Boots

GET_LOCK('tuv_schema_migration', 30) serialisiert gleichzeitig startende Prozesse.

Desired State — idempotent bei jedem Start

Stammdaten-Seeds (INSERT IGNORE) und der WF-01-Trigger (CREATE OR REPLACE TRIGGER) werden bei jedem Serverstart neu deklariert. Konsequenz: Eine Trigger-Korrektur erreicht jede Installation beim nächsten Start — ohne Migration.

Kein Down-Pfad

Rollback läuft über das Backup-Konzept (Binlog + Dump), nicht über ungetestete Reverse-Migrationen. Ein Downgrade auf einen älteren Stand ist nicht vorgesehen (CHANGELOG 1.0.0).

Warum kein Flyway/Liquibase?

MariaDB hat kein transaktionales DDL — der Hauptvorteil schwerer Frameworks existiert dort gar nicht. Was bleibt, ist Buchführung plus Reihenfolge: rund 60 Zeilen. Konsequenz: jede Migration muss wiederholbar sein, falls sie mittendrin abbricht.

Beim Restore relevant: Weil der Trigger Desired State ist, wird er beim nächsten Start ohnehin neu gesetzt — trotzdem prüft restore.sh ihn direkt nach dem Einspielen. Siehe B12.

Anhang B4 · Authentifizierung

Anmeldung im Detail — scrypt und HMAC-Token

Bewusst ohne Zusatz-Abhängigkeiten, nur node:crypto: Das On-Premise-Deployment soll ohne native Build-Toolchain auskommen, und server/auth.js bleibt als reines Funktionsmodul ohne DB-Zugriff unit-testbar.

Passwörter: scrypt, Parameter im Hash

Format scrypt$N$r$p$salt$hash (N = 16384). Die Parameter stehen im Hash selbst und können später erhöht werden, ohne bestehende Hashes zu invalidieren. Beim Parsen greifen Plausibilitätsgrenzen — ein manipulierter DB-Wert kann scrypt nicht mit absurden Parametern aufrufen.

Token: HMAC-SHA256, 12 Stunden

base64url(payload).base64url(HMAC-SHA256(payload)) · Payload: Kürzel, Name, Rolle, Ablauf. JWT-artig, aber kein Standard-JWT — kein Header-Segment, fester Algorithmus, ein alg=none-Downgrade ist strukturell ausgeschlossen. Preis: kein Format, das andere Systeme lesen.

Timing-sichere Vergleiche

timingSafeEqual bei Passwort-, Token- und Admin-Token-Vergleich; beide Seiten werden vorher gehasht, damit die Puffer gleich lang sind. Unbekannte Kürzel rechnen trotzdem ein scrypt gegen einen Dummy-Hash — die Antwortzeit verrät nicht, welche Konten existieren.

Wann Auth aktiv ist

AUTH_ENABLED ohne Wert: an bei NODE_ENV=production, aus in Entwicklung und CI (dort laufen Requests als Dev-Chef, damit die Integrationstests ohne Login funktionieren). Das Docker-Deployment setzt NODE_ENV=production. In den E2E-Tests wird Auth explizit eingeschaltet — sonst wären die Rollen-Journeys nicht prüfbar.

Fail-fast beim Start

Produktion ohne ADMIN_TOKEN, oder Auth aktiv ohne Secret → process.exit(1) mit klarer FATAL-Meldung. Beide Guards sind mit echten Prozess-Tests abgedeckt. Grundsatz aus den Code-Kommentaren: lieber laut kaputt als leise unsicher.

Keine Enumeration, Brute-Force gebremst

Gemeinsame 401-Meldung für „Kürzel unbekannt“ und „Passwort falsch“ · Login-Rate-Limit 10 Versuche / 15 Minuten in Produktion.

Offen

kein Token-Widerruf (zustandslos, 12 h) · kein Passwort-Self-Service · Token im localStorage · keine Passwortrichtlinie, keine 2FA.

Dokumentierte Regeln und wo sie erzwungen werden

Aus docs/datenmodell.md § 2.5. Es gibt genau eine Regel, die nicht deklarativ ausdrückbar ist — WF-01. Alle anderen liegen als Constraint im Schema.
IDRegelLogische AusdrucksformErzwingung
GR-01Kennzeichen ist eindeutigUNIQUE(kennzeichen) auf FAHRZEUGdeklarativ
GR-02FIN ist eindeutigUNIQUE(fin); mehrere NULL sind in MariaDB erlaubtdeklarativ
GR-03WF-01 — kein „Bestanden“ bei offenem EM/GfMrelationsübergreifend, nicht als einfacher CHECK ausdrückbarUI API DB-Trigger

Warum GR-03 anders ist: Ein CHECK darf in MariaDB nur Werte derselben Zeile prüfen. WF-01 ist eine Bedingung über eine andere Tabelle — deshalb der Trigger, deshalb die drei Ebenen. Alle anderen Regeln brauchen keinen Code.

Es gibt keine WF-02 bis WF-05. Im Repository ist genau eine Workflow-Regel als WF-01 benannt (Pflichtenheft F-05, ADR-003). Weitere fachliche Anforderungen sind als F-01…F-11 dokumentiert, aber nicht als Workflow-Regeln in diesem Sinn.

Anhang B6 · WF-01-Implementierung

Die drei Ebenen im Quelltext

Ebene 2 · Express — PATCH /api/termine/:id/status
if (neuerStatus === "Bestanden") { const blocker = await one( `SELECT COUNT(*) AS count FROM mangel m JOIN mangel_kategorie mk ON mk.kategorie_code = m.kategorie_code WHERE m.termin_id = ? AND mk.blockiert_bestanden = TRUE AND m.behoben = FALSE`, [req.params.id]); if (Number(blocker?.count ?? 0) > 0) { res.json({ ok: false, reason: "BESTANDEN nicht möglich …" }); return; } }

Bewusst HTTP 200: Die fachliche Ablehnung ist kein Protokollfehler, das Frontend bekommt einen einheitlichen Vertrag { ok, reason }. Kritikpunkt, den wir selbst nennen: 409 oder 422 wären eine legitime, in REST üblichere Modellierung.

Ebene 3 · MariaDB — server/db.js, Desired State
CREATE OR REPLACE TRIGGER trg_termin_wf01_update BEFORE UPDATE ON termin FOR EACH ROW BEGIN IF NEW.status_code = 'Bestanden' AND OLD.status_code <> 'Bestanden' THEN IF EXISTS ( SELECT 1 FROM mangel m JOIN mangel_kategorie mk ON … WHERE m.termin_id = NEW.termin_id AND mk.blockiert_bestanden = TRUE AND m.behoben = FALSE) THEN SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'WF-01: BESTANDEN nicht moeglich …'; END IF; END IF; END

Ebene 1 · React

Die Schaltfläche „Bestanden“ ist disabled, wenn ein unbehobener blockierender Mangel am Termin hängt; der Titel nennt § 29 StVZO. Der E2E-Test prüft genau diese beiden Eigenschaften.

Die bewusst benannte Grenze

Der Trigger hängt an BEFORE UPDATE ON termin. Wird per direktem SQL ein blockierender Mangel zu einem bereits bestandenen Termin eingefügt, greift er nicht — diesen Fall behandelt POST /api/maengel transaktional.

Sicherheitsnetz im Fehler-Handler

Löst der Trigger doch aus (z. B. nebenläufig eingefügter Mangel zwischen Blocker-Prüfung und UPDATE), mappt der zentrale Handler SQLSTATE 45000 auf HTTP 422.

Anhang B8 · SQL-Bypass

Der Test, der die eigene Anwendung aus dem Weg nimmt

Und die Geschichte, warum er lange existierte, ohne etwas zu beweisen.
server/tests/dbCli.js — Zugriffsweg zur Laufzeit
/* Reihenfolge: * 1. Direkter MariaDB/MySQL-Client über TCP * (CI, lokales Setup ohne Docker) * 2. docker exec <container> mariadb ... * (Compose-Stack) * 3. null — Aufrufer skippt mit klarer Begründung */

Vorher: ein Layer ohne Nachweis

Der Aufruf war fest auf docker exec tuv-mariadb verdrahtet. In der CI läuft MariaDB als Service-Container, nicht über Compose — also gab es diesen Container nicht, und der Test wurde per TUV_SKIP_SQL_BYPASS übersprungen. Ein Defense-Layer, der in der Pipeline nie geprüft wird, ist kein geprüfter Layer.

Heute

Der Zugriffsweg wird zur Laufzeit gewählt. Übersprungen wird nur, wenn es gar keinen Weg gibt — und selbst das würde die Pipeline auffliegen lassen.

Anhang B9 · Transaktionen & Nebenläufigkeit

Was atomar ist — und was ausdrücklich nicht

Transaktional (withTransaction)

  • POST /api/maengel — INSERT Mangel + ggf. Rückstufung des Termins
  • POST /api/admin/demo — Seed der Beispieldaten
  • POST /api/admin/reset — vier DELETEs in FK-sicherer Reihenfolge

Ausdrücklich nicht transaktional

  • Frontend-Abläufe aus mehreren HTTP-Requests (z. B. „Halter anlegen, dann Fahrzeug anlegen“)
  • Es gibt keinen zusammengesetzten Endpunkt dafür — wäre der Kandidat, falls es fachlich wichtig würde

Isolation

InnoDB-Standard REPEATABLE READ, nicht bewusst geändert. Für die Größenordnung einer Prüfstelle (5–20 gleichzeitige Nutzer) war das kein Engpass.

Verbindungen kommen aus einem Pool; ohne COMMIT rollt MariaDB beim Abbruch zurück. Der Code macht zusätzlich im catch ein explizites ROLLBACK und gibt die Verbindung im finally frei.

Mehrbenutzer-Verhalten im Frontend

Polling alle 5 Sekunden (src/hooks/useDb.ts), pausiert bei Hintergrund-Tab und während eines eigenen Schreibvorgangs (writeInFlight-Zähler) — sonst könnte ein Poll-Tick mit altem Stand den laufenden Schreibvorgang überschreiben. Optimistische Updates merken sich den Vorzustand und rollen bei Ablehnung zurück.

Ehrliche Grenze — keine Konflikterkennung

Es gibt heute keine Zeilenversion und kein ETag. Bearbeiten zwei Clients dasselbe gewöhnliche Feld, gewinnt effektiv der letzte Schreibvorgang. Wir behaupten nicht, dass die Mehrbenutzer-Bearbeitung konfliktfrei ist. Was trotzdem geschützt ist: WF-01 hängt nicht am Client-Zustand — API und Trigger prüfen beim Statuswechsel den aktuellen Datenbankstand.

Anhang B10 · Sicherheit

Härtung — und die bekannten Grenzen aus SECURITY.md

helmet + CSP

Security-Header ab Werk. Die CSP verbietet Inline-Scripts; upgrade-insecure-requests ist entfernt, weil das LAN-Modell bewusst über HTTP läuft.

Rate-Limits (nur Produktion)

/api 600/min · /api/admin 30 / 15 min · /api/auth/login 10 / 15 min. In Dev/CI aus, damit Integrationstests nicht anschlagen.

CORS auf das LAN begrenzt

Statt Wildcard: localhost, 127.0.0.1 und private RFC-1918-Netze plus optionale Whitelist über ALLOWED_ORIGINS.

Fehler-Semantik ohne SQL-Leak

Duplikat → 409 · fehlende Referenz → 400 · CHECK-Verstoß → 400 · Trigger-SIGNAL → 422. 500er geben keine err.message an den Client.

Kleine Angriffsfläche

DB-Port nur 127.0.0.1 · Adminer nur über ein Compose-Profil · Admin-Endpunkte doppelt geschützt (Chef-Rolle und X-Admin-Token) · express.json auf 1 MB · durchgängig parametrisierte Queries.

Health mit Substanz

GET /api/health prüft die Datenbank per SELECT 1 — sonst meldet der Endpunkt „ok“, während MariaDB längst weg ist.

Bekannte Grenzen — SECURITY.md § 9, unverändert übernommen

  • Kein HTTPS im LAN. Anmeldedaten sind für Mitlesende im selben Netz sichtbar.
  • Kein physischer Schutz. Wer Zugang zum Server-PC hat, hat Zugang zur Datenbank.
  • Keine Token-Rücknahme. Ein Token gilt bis zu 12 Stunden, auch wenn das Konto gesperrt wird.
  • Kein Änderungsprotokoll. Es ist nicht nachvollziehbar, wer ein Prüfergebnis gesetzt hat.
  • Keine Passwortrichtlinie, keine 2FA.
  • Ein gemeinsamer Admin-Token statt persönlicher Administratorkonten.
  • Kein Schutz gegen einen böswilligen Prüfer. Wer die Rolle hat, darf Mängel entfernen und danach „Bestanden“ setzen. Dagegen hilft nur ein Audit-Log, keine technische Sperre.

Anhang B11 · Betrieb

On-Premise-Deployment

Jede Prüfstelle betreibt docker-compose.yml auf einem Server-PC im lokalen Netz.
services: db: image: mariadb:11.4 container_name: tuv-mariadb # Port nur an localhost: die API erreicht MariaDB über # das interne Docker-Netz, Clients im LAN nie direkt. ports: [ "127.0.0.1:3306:3306" ] volumes: mariadb_data · my.cnf (Binlog) · ./backups api: image: node:24-alpine # Docker-Deployment = Kunden-Deployment → production. # Ohne NODE_ENV lief der Container im dev-Modus und der # Fail-fast-Guard griff nie — /api/admin/* waere still # oeffentlich gewesen. NODE_ENV: production API_PORT: 8787 volumes: ./dist (gebautes Frontend wird mit ausgeliefert)

Netzwerkbild

  • Arbeitsplätze und Tablets → http://<server-ip>:8787
  • Express liefert API und gebautes Frontend aus dist/
  • Port 5173 ist der Vite-Entwicklungsserver und läuft beim Kunden nicht
  • MariaDB ist im WLAN nicht sichtbar

Laufzeit

Node 24 (Active LTS) im Image, in allen Workflows und in der Dokumentation. engines.node >= 22. Node 20 ist seit dem 30.04.2026 End-of-Life und bekommt keine Sicherheitsfixes mehr.

Optional: Tauri

Eine Desktop-Hülle (src-tauri/) um dasselbe gebaute Frontend, falls ein Arbeitsplatz lieber ein Fenster als einen Browser-Tab hätte. Der ausgelieferte Betriebsweg ist Docker Compose.

Trade-off: Die Prüfstelle verantwortet Backups, Updates und LAN-Sicherheit selbst — dafür laufen die operativen Daten nicht über einen Auftragsverarbeiter. Sobald ein Offsite-Backup aktiv wird, kommt dieser Punkt zurück auf den Tisch.

Anhang B12 · Backup-Format & Verifikation

Was genau geschrieben, geprüft und wiederhergestellt wird

scripts/backup.sh — Tier 2

  • voller Dump mit Triggern, AES-256-CBC, PBKDF2 mit 200 000 Runden
  • Rotation 7 täglich / 4 wöchentlich / 12 monatlich
  • je Sicherung eine .meta-Datei mit klartext_sha256
  • ohne Schlüssel bricht das Skript ab, statt Klartext mit Halterdaten zu schreiben

scripts/restore.sh — Ein-Befehl-Restore

  • entschlüsseln, dann Prüfsumme vor dem Überschreiben gegen die .meta vergleichen
  • Ziel-Datenbank neu anlegen, einspielen
  • danach: Tabellenzahl und Existenz des WF-01-Triggers prüfen — fehlt er, bricht das Skript mit Fehler ab
  • Rückfrage vor dem Überschreiben einer Produktionsdatenbank

Der Grund für die Trigger-Prüfung: Ein Dump ohne --triggers spielt sich ohne sichtbaren Fehler ein. Die Daten wären vollständig, WF-01 wäre weg — und niemand würde es merken, bis jemand ein falsches „Bestanden“ setzt.

Der Drill in sieben Schritten

  • Fingerabdruck der Quell-DB (normalisierter Dump, sha256)
  • verschlüsseltes Backup schreiben
  • DROP DATABASE — wirklich, nicht simuliert
  • Restore über restore.sh
  • Fingerabdruck vergleichen — muss identisch sein
  • Zeilenzahlen aller Tabellen; Trigger existiert und greift (gesperrtes UPDATE muss scheitern)
  • Gegenprobe: beschädigtes Backup muss abgelehnt werden

Schutz gegen Unfälle

Der Drill läuft nur gegen eine Datenbank, deren Name mit tuv_drill beginnt — oder mit explizit gesetztem TUV_DRILL_ERLAUBE_ZIEL_DB. Sonst könnte ein Tippfehler die Produktionsdatenbank löschen.

Zwei Zugriffswege, aus gutem Grund

Ein CI-Job mit installiertem MariaDB-Client, ein zweiter erzwungen über TUV_DB_MODUS=docker. Genau der zweite deckte auf, dass die Verbindungsprobe des Container-Wegs ohne Passwort anfragte und deshalb nie funktionierte — auf einem Kunden-Server-PC ohne Client hätte das bedeutet: kein Backup, kein Restore.

Offen (docs/backup.md § 7)

Zeitsteuerung am Server-PC (cron / Aufgabenplanung — gehört ins Kunden-Setup) · sync-offsite.sh für Tier 3 · Alarmierung bei Fehlschlag am Standort · Point-in-Time-Recovery über Binlogs ist konfiguriert, aber Handarbeit und nicht automatisiert geprüft.

Anhang B13 · End-to-End

Playwright — 6 Journey-Dateien · 25 Tests

// eigene Ports statt der Entwicklungs-Ports API_PORT = 8788 WEB_PORT = 5174 DB = tuv_e2e AUTH_ENABLED = true // im Dev-Default waere sie aus — ohne Login liessen sich // die Rollen-Journeys gar nicht pruefen fullyParallel: false workers: 1 // die Specs teilen eine DB und setzen sie pro Datei neu auf projects: chromium (Desktop) · tablet (820×1180, hasTouch) retries: CI ? 1 : 0 · trace/video: retain-on-failure

Warum eigene Ports?

Auf einer Entwickler-Maschine läuft auf 8787 oder 5173 oft schon etwas anderes. Ein E2E-Lauf, der versehentlich gegen einen fremden Dienst testet, ist schlimmer als einer, der gar nicht startet.

Warum Chromium statt iPad-Profil?

Ein iPad-Profil würde WebKit laden — ein zweiter Browser-Download in jeder Pipeline, und die Aussage wäre trotzdem nur „Safari-Engine“. Geprüft wird das Layout bei 820 px mit Touch.
